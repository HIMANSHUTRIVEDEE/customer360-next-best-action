## Architecture Critique and Simplification

### Critique

#### 1. Excessive Complexity for a Six-Day Build

| Over-engineered element | Problem | Simplification |
|------------------------|---------|----------------|
| **6 schemas** (RAW, CURATED, AI_ENRICHED, SERVING, DECISION, CONFIG) | Each schema needs DDL, grants, pipeline logic, and testing. 6 schemas × role grants × pipeline stages = combinatorial work. | **Collapse to 3 schemas:** RAW, ANALYTICS (replaces CURATED + AI_ENRICHED + SERVING), DECISION. CONFIG becomes a set of tables within ANALYTICS. |
| **SCD Type 2 on DIM_CUSTOMER and DIM_POLICY** | SCD2 requires merge logic, valid_from/valid_to management, is_current filtering on every query, and synthetic data that exercises version transitions. | **Drop SCD2 entirely.** With synthetic data and a 6-day window, no record will actually change. Use simple tables. Document SCD2 as a production enhancement. |
| **Dynamic tables for CURATED layer** | DTs from RAW → CURATED add a processing hop before you reach the 360 view. Two DT layers (CURATED DTs + SERVING DT) means two lag windows and two points of failure. | **One dynamic table total:** CUSTOMER_360_VIEW reads directly from base tables + enrichment. Skip the intermediate curated DTs. Load synthetic data directly into final-shape tables. |
| **Separate TRANSCRIPT_CONTENT and ENRICHMENT_RESULT tables** | Two tables + FK + join for what is functionally one enrichment pass. | **Merge into one table:** INTERACTIONS_ENRICHED with raw_text + sentiment columns. Access-tier separation is a RBAC concern (column masking), not a table-separation concern. |
| **CONTEXT_SNAPSHOT as JSON blob** | Requires application code to serialize the entire 360 state, store it, and deserialize for audit replay. Significant dev effort for an audit feature that won't be exercised in a demo. | **Defer to bonus.** For MVP, the RECOMMENDATION_LOG captures customer_id + timestamp — reviewers can query the 360 view with TIME TRAVEL to approximate the snapshot. |
| **DECISION_AUDIT_EVENT (separate from FOLLOW_UP_LOG)** | Two tables for decision tracking when one suffices for demo. | **Merge into one DECISION_LOG** with a `decision_type` column (approved, modified, rejected). Every action goes in one table. |
| **EligibilityRule as a separate entity** | Requires a config table, lookup logic in the NBA engine, and test coverage for rule filtering. | **Hardcode eligibility in the NBA engine logic** as Python constants. Document the rules. Externalize to a table in production. |

**Net result:** ~26 tables reduced to ~12. Pipeline stages reduced from 4 hops to 2. Role grants simplified from 6 schema × 4 roles to 3 schema × 3 roles.

#### 2. Missing Dependencies

| Gap | Risk | Fix |
|-----|------|-----|
| **No warehouse sizing specified** | Dynamic tables and Cortex functions need compute. If the warehouse is too small or suspended, the demo fails on stage. | Specify: one XS warehouse for pipeline, one XS for Streamlit queries. Auto-resume enabled. Document in setup script. |
| **No Cortex function availability check** | SNOWFLAKE.CORTEX.SENTIMENT() and COMPLETE() may not be available in all regions or account tiers. | Add a pre-flight check script that validates Cortex availability before setup proceeds. Document fallback if unavailable. |
| **No Streamlit-in-Snowflake deployment path** | The architecture assumes SiS but doesn't specify how the app gets deployed (snow CLI? manual?). | Use `snow streamlit deploy` via CoCo. Add to setup sequence. |
| **Synthetic data generator has no specified runtime** | Python script — but where does it run? Locally? In a Snowflake task? In a notebook? | Run locally via CoCo bash, output to staged CSVs, COPY INTO RAW tables. Simple, reproducible. |
| **No connection/session configuration** | Demo needs a specific database, schema, role, warehouse active. If the session drifts, queries fail. | Add a `USE` preamble or session-initialization SQL at the top of every script and in the Streamlit app. |

---

#### 3. Security Gaps

| Gap | Risk | Fix |
|-----|------|-----|
| **Column masking not specified for PII** | Transcript raw_text contains PII. Even with synthetic data, demonstrating masking shows enterprise readiness. | Apply dynamic data masking on raw_text column for AUDITOR role. Rep sees full text; auditor sees masked. One policy, high demo value. |
| **No row-level security** | SERVICE_REP can query all customers. In production, reps see only their assigned customers. | **Accept for MVP.** Document as production enhancement. Not needed for single-rep demo. |
| **Application writes to DECISION schema without service account** | If the Streamlit app runs as the user's role, that role needs INSERT on DECISION tables — blurring the RBAC model. | Create a `SERVICE_APP` role that owns DECISION writes. Streamlit runs with this role. Rep's personal role is read-only on SERVING. |
| **No network policy** | Low risk for prototype, but shows governance awareness. | **Defer.** Not visible in demo, not needed for synthetic data. |

---

#### 4. Unsupported AI Decisions

| Issue | Severity | Fix |
|-------|----------|-----|
| **Sentiment score directly used as a risk signal weight** | Medium. Cortex SENTIMENT() returns a score but its correlation to actual churn risk is unvalidated. Using it as a weighted input implies calibration that doesn't exist. | Label sentiment as an **indicator**, not a **predictor**. The NBA engine uses presence/absence of negative sentiment (binary), not the continuous score. Show the score for transparency but don't weight it as if calibrated. |
| **Confidence score formula undefined** | The architecture claims a confidence level but doesn't specify the formula. "High confidence" based on 2 signals and 50 synthetic transcripts is not meaningful. | Define confidence as: `signal_count / expected_signal_count` (data completeness). Drop the pretense of statistical confidence. Call it "evidence completeness" instead. |
| **Topic extraction quality unvalidated** | Cortex EXTRACT_ANSWER or COMPLETE for topic extraction may produce inconsistent topics across similar transcripts. | For MVP: extract topics using a fixed prompt with constrained output categories (billing, claims, coverage, service, general). Reduces variance. Show raw output; don't use topics in scoring. |

---

#### 5. Poor Explainability

| Issue | Fix |
|-------|-----|
| **Evidence payload is a JSON blob** | The rep can't interrogate it. The Streamlit app must parse and render it. If the rendering is poor, "explainability" is just data dumped on screen. | Design the evidence display as 3 specific bullets max: (1) "Renewal in N days", (2) "N negative interactions in last 90 days", (3) one supporting quote from transcript. Hard-code the format. |
| **Alternative actions have no differential explanation** | "Escalate to retention specialist" is shown as an alternative but there's no explanation of *why it's ranked lower*. | For each alternative, show one sentence: what signal would need to be different for this to be the top action. e.g., "Would be recommended if sentiment were more severe." |
| **Risk signal weights are invisible to the rep** | The weights are in CONFIG but never surfaced. | Show a simple bar chart: each signal's contribution to the overall score. Visual > numeric. |

---

#### 6. Demo Risks

| Risk | Likelihood | Impact | Mitigation |
|------|-----------|--------|-----------|
| **Cortex function cold-start latency** | High (first call in a session can take 5-10s) | 360 view renders slowly on first customer lookup | Warm up Cortex with a dummy call during app initialization |
| **Dynamic table lag** | Medium (15-min TARGET_LAG means data may be stale during live demo) | Inserted interaction doesn't appear immediately | For live demo, query base tables directly with a UNION to the DT. Or reduce TARGET_LAG to 1 minute for demo warehouse. |
| **Synthetic data doesn't cover edge cases** | Medium | Demo works for Maria Chen but fails for any other customer selection | Seed 3-5 fully fleshed scenarios covering: happy path, no interactions, all positive, missing enrichment (fallback demo). Test all before demo. |
| **Streamlit session timeout** | Low-Medium | If demo pauses too long, session drops and state resets | Add session state persistence via st.session_state. Keep warehouse auto-resume on. |
| **Judge asks "what happens if AI is wrong?"** | High (judging criteria: real-world relevance) | Weak answer undermines credibility | Prepare: (1) AI only provides sentiment indicator, not the decision. (2) Human always approves. (3) Show fallback live by toggling enrichment off. |

### Simplified Architecture (what to write in docs/architecture.md)

**3 schemas, not 6:**
```
CUSTOMER360_DB
├── RAW           -- Synthetic data landing (simple tables, no pipeline)
├── ANALYTICS     -- Enrichment + 360 dynamic table + config tables
└── DECISION      -- Immutable recommendation/follow-up/outcome log
```

**2 pipeline stages, not 4:**
```
RAW tables (loaded once by setup script)
    │
    ▼ [Dynamic Table: ANALYTICS.INTERACTIONS_ENRICHED]
    Cortex SENTIMENT() applied to transcripts
    │
    ▼ [Dynamic Table: ANALYTICS.CUSTOMER_360]
    Joins all RAW tables + enrichment into pre-aggregated 360
    │
    ▼ [Application reads CUSTOMER_360 → computes signals → generates NBA → presents to rep]
    │
    ▼ [Rep approves → writes to DECISION.DECISION_LOG]
```

**3 roles, not 4:**
- `DATA_ENGINEER`: owns RAW, ANALYTICS. Runs setup.
- `SERVICE_APP`: reads ANALYTICS, writes DECISION. Used by Streamlit.
- `AUDITOR`: reads DECISION + ANALYTICS (with masking on PII columns).

**Trust boundary:**
```
┌─────────────────────────────────────┐
│  DETERMINISTIC ZONE                 │
│  (rules engine, eligibility,        │
│   signal weights, scoring)          │
│  → Always produces same output      │
│    for same input                   │
│  → Fully auditable                  │
└──────────────────┬──────────────────┘
                   │ consumes
┌──────────────────▼──────────────────┐
│  GENERATIVE AI ZONE                 │
│  (Cortex SENTIMENT, topic extract)  │
│  → Labeled as machine-derived       │
│  → May fail (fallback path exists)  │
│  → Never overwrites source data     │
│  → Used as indicator, not decision  │
└─────────────────────────────────────┘
                   │ presented to
┌──────────────────▼──────────────────┐
│  HUMAN APPROVAL GATE                │
│  → Rep sees recommendation          │
│  → Rep approves/modifies/rejects    │
│  → No action without consent        │
└─────────────────────────────────────┘
```

**What's deferred (still enterprise-credible if documented):**
- SCD Type 2 → documented as production enhancement
- ContextSnapshot → documented, use TIME TRAVEL for prototype audit
- Separate enrichment table → column masking on combined table
- EligibilityRule table → hardcoded in Python, documented for externalization
- Row-level security → documented
- Network policy → documented

This produces a buildable system in 6 days while the documentation shows the reviewer you've *thought about* the enterprise concerns and made conscious trade-offs.
